# ChaosProxy + PhotoTask：代码约束与防膨胀规则

> 版本：V1.0 · 2026-09-12。
> 配套：《ChaosProxy_PhotoTask_统一代码实现蓝图与长期教学提示词.md》。
> 适用：原 ChaosProxy、照片任务服务、MySQL/Redis、Nginx、Kafka，以及配套测试和工具。
> 目的：让每一段新增代码对应真实职责，控制抽象、重复实现和辅助工程的规模。
> 状态：这是后续实施与审查规则；尚未审查真实仓库，不表示已有代码存在下文列举的问题。

## 1. 总原则与约束效力

**保留完整业务与正确性，通过复用成熟实现、减少重复逻辑和缩短无效调用链控制代码量。**

本文件细化蓝图的实现约束。发生冲突时：

1. 用户当前明确要求优先。
2. 已确认功能、故障语义和正确性不变量必须保留。
3. 本文件约束“如何实现”，不自动授权删除功能。
4. 蓝图中的类名、接口与目录是设计方向，不是必须逐项创建的清单。

“超预算”触发设计复查，不是停止工作的硬门槛。完成必要代码、保留测试并记录理由后可以继续；不因一个软阈值反复要求用户批准。

禁止靠压缩排版、删除空行、缩短命名、滥用宏、合并无关职责或删除异常处理降低统计数字。函数变少不一定更简单，代码行数也不能代替设计判断。

## 2. 代码预算与统一统计

### 2.1 完整版本的设计预算

完整版本包括已规划的 Kafka 阶段。以下为项目内审查预算，不是行业标准或已经测量的结果。

| 模块 | 目标核心代码量 | 必须包含 |
|---|---:|---|
| ChaosProxy I/O、连接、缓冲与调度 | 2,300 行 | token、背压、半关闭、公平续跑 |
| 故障策略、定时器、控制与轨迹 | 1,500 行 | continuation、取消、版本与 ACK |
| PhotoTask API、MySQL、Redis、Outbox | 2,700 行 | 幂等、事务、回源保护与补偿 |
| Worker、图像适配、结果与恢复 | 1,500 行 | lease、attempt、条件提交 |
| Kafka 发布、接入与位点 | 1,000 行 | delivery、inbox、rebalance、隔离 |
| **合计目标** | **9,000 行** | 含必要薄适配和公共错误处理 |

共用代码归入一个主要责任模块，不在多个模块重复统计。7,000～11,000 行是此前的粗估区间，9,000 行是用于约束设计的中间目标，不是保证。

- 模块超过目标 25%：检查重复实现、框架包装与提前建设，并说明剩余阶段。
- 核心代码超过 11,000 行：做一次全局职责审查，重点检查辅助设施是否超过业务与协议本身。
- 正确性修复可以使代码增长；记录新增不变量与验证证据，不要求为了抵消新增行数强行删代码。

### 2.2 统计口径

核心代码统计自己维护的生产 C++ 头文件和源码，包括模板、公共工具、适配层与可执行入口；排除空行、纯注释、第三方源码、构建目录和自动生成代码。

单独记录，不计入上述 9,000 行目标：测试 C++、Python Runner、SQL migration、手写 .proto、CMake/部署配置。它们仍属于项目成本，不能把业务实现移动到脚本或代码生成模板后宣称代码消失。

使用同一工具与同一目录排除规则，例如固定使用 cloc 的 code 列；报告工具版本、commit 和目录口径。未安装统计工具时可以先记“未测量”，不得把 wc -l 原始行数当作同一统计口径。

每个里程碑记录一次模块增量。每次改动只做简短变更说明，不建立新的指标平台、统计数据库或复杂 CI 门禁。

## 3. 新增代码前的四问

开始实现前，教师或编码助手必须回答：

1. 这次新增的用户行为、故障处理或不变量是什么？
2. 仓库中哪个模块已经承担相近职责，能否在它内部完成？
3. 使用现有库/现有实现，还缺哪一段必须自己写的逻辑？
4. 哪个实际测试或运行结果能证明这次改动有用？

只需要围绕当前改动回答，不展开整份架构。若答案只是“更通用”“以后可能扩展”“看起来更工程化”，先不创建新框架。

新增逻辑首先考虑普通函数或现有具体类的方法。只有需要独立状态、资源所有权、业务边界或可验证的替换点，才创建新类。

## 4. 类、接口与分层约束

### 4.1 接口准入

满足下列任一明确理由，才为生产代码建立抽象接口：

- 当前确实有两个实现，并且调用者需要统一使用。
- 必要的确定性/故障测试需要替换外部边界，例如 Clock、FileOps、RandomSource。
- 需要隔离第三方类型或生命周期，使领域层不依赖具体客户端。

单个实现不自动意味着接口应删除；必须结合上述理由判断。反过来，测试里能写一个 Mock 也不能单独证明接口有必要。

禁止为每个类同步建立 IClass、ClassImpl、ClassFactory、ClassManager。禁止只转发参数、不改变边界也不管理资源的连续包装。

### 4.2 推荐调用层次

业务：Controller → 用例/Service → Repository 或客户端适配。

代理：Reactor 分发 → ConnectionPair/Direction 推进 → Socket 与策略实现。

这些是职责层次，不是严格函数调用次数限制。异步回调、错误映射、RAII helper 可存在；要能解释每一层增加了什么约束或负责什么资源。

同一 SQL 操作不同时经过 DAO、Repository、Store、Gateway 四层同义对象。参数校验、事务与 SQL 分层可以保留，但不要把一个简单查询拆成五个只调用下一层的类。

### 4.3 目录与文件

- 一个小型紧密相关值类型集合可放在同一头文件；不强制一个 enum 一个文件。
- 单文件局部工具留在匿名命名空间，只有跨文件复用或独立边界成立才导出。
- 不把所有局部 helper 提升成公共 utils API；不因匿名命名空间本身存在就重构。
- 单个源码约 600 行、函数约 100 行时触发阅读性检查，均为提示阈值。
- 只按职责拆分；一段清晰 SQL、协议状态分支或集中错误映射可以超过提示值，不为满足数字拆成碎片。
- 拆文件通常不减少总代码量，不把“文件数增加”当作收敛成果。

## 5. 自己实现与成熟库的分工

| 内容 | 采用方式 | 限制 |
|---|---|---|
| epoll Reactor、背压、连接生命周期 | 自己实现 | 保留项目核心，不再写第二套并行模型 |
| TimerQueue、Token Bucket、Toxic continuation | 自己实现 | 不同时维护多种未使用算法 |
| HTTP、MySQL、Redis 客户端 | 复用蓝图选定的成熟库 | 薄适配，不复制客户端连接池 |
| Kafka 协议与生产消费客户端 | librdkafka 适配 | 不手写 broker 协议与重传机制 |
| JSON、Protobuf、图片编解码 | 成熟库 | 自己校验业务字段、输入范围和版本 |
| 幂等事务、Outbox、admission、任务 lease | 自己实现业务协议 | 不把数据库约束误认为库会自动补齐 |
| 日志、测试、CLI、监控格式 | 复用框架 | 不建立自研插件平台、断言框架 |

薄适配可以负责资源释放、错误映射、线程投递、容量和 deadline。禁止把第三方库的全部方法逐个重新命名暴露一遍。

依赖未提供某项真实所需能力时，先证明缺口，再选择补适配或替换库；不把“减少代码”解释成无条件相信框架保证正确性。

## 6. ChaosProxy 专项约束

### 6.1 两个方向使用一份推进实现

client_to_upstream 与 upstream_to_client 使用同一个 Direction 类型和 Pump 路径，端点映射作为数据传入。禁止复制一套 ClientRead/ServerRead、ClientWrite/ServerWrite 的同构业务流程。

连接错误、建连、半关闭等确有不同状态的分支可以保留。共享代码不得掩盖方向语义；不能为合并而让调用者到处传互相矛盾的 bool 参数。

### 6.2 单一所有权与关闭出口

- Reactor owner 负责连接状态和 fd 关闭。
- 同一连接的关闭协议集中维护，原因通过 CloseReason 表达。
- timer、事件和 continuation 都复用同一个连接身份验证规则。
- 不为每种 Toxic 各建 ConnectionRegistry、TimerManager 或独立线程。
- Endpoint 与 Direction 分别表达 TCP 端点和转发方向，不能为减少类数合并到无法区分半关闭的结构。

### 6.3 策略复用边界

Latency/Jitter 共用延迟入队和到期释放；Bandwidth 共用定时唤醒与 Buffer view；Close/Reset 共用清理协议但保留不同关闭语义。

禁止每个策略复制一套读写循环、timer 容器、队列预算和错误处理。新增策略只实现它改变的行为。

首版使用已确认的策略组合，不编写动态库插件加载、任意策略依赖图或通用规则表达式引擎。需要新增组合时，先增加一个具体场景与相应约束。

### 6.4 性能实现只保留当前必要路径

最小堆与时间轮不同时作为默认维护目标。新实现通过真实比较后选定一条主路径；若保留基准对照，明确放在实验范围，不使生产接口为两套实现持续膨胀。

多 Reactor 不复制连接业务，只增加 owner 分片与命令投递。Buffer Pool 不衍生通用 allocator 框架。控制 UDS 不需要再写一套 HTTP Server。

## 7. PhotoTask 与中间件专项约束

### 7.1 用例与模型

- DTO 只表达实际 API 输入输出；数据库行和 domain 的差异不存在时，不机械维护多套同形对象。
- owner_scope、task_id、generation、epoch 等有正确性意义的字段保留。
- 强类型 ID 有助于避免混用时保留；不为所有字符串与整数各建模板框架。
- Task 状态是一个权威模型；HTTP 展示、Kafka event、数据库值需要映射时集中定义。
- 不为“照片任务”额外建立项目未要求的用户中心、支付、权限平台或搜索平台。

### 7.2 MySQL 和事务

CreateTask 的幂等记录、task 与 Outbox 由一段明确的事务用例维护，Repository 提供必要操作。禁止每个表一个通用 CRUD Service，再让事务散布在多个 Service 中。

短事务 helper 可以复用开始/完成/错误处理；业务 SQL、行锁条件和提交不确定的处置必须可见。禁止使用隐藏事务边界的万能 ExecuteWithRetry 包住所有业务。

schema migration 只维护一份权威定义。已经在共享环境执行的 migration 不为了“减少文件”改写历史；可整理新环境基线，但必须保留版本升级路径。

### 7.3 Redis

只实现已使用的 Get/Put/Invalidate、期限和错误语义，不封装完整 Redis API。

singleflight、回源准入和熔断可复用一个明确的请求状态，但三者职责不能因名称相近而合并：去重、容量限制与故障探测是不同约束。

缓存只覆盖蓝图允许陈旧的照片资料；不要为任务状态、幂等记录和所有数据库表自动生成缓存层。不要额外增加本地 L1 缓存、分布式锁和多级失效总线来解决尚未出现的问题。

### 7.4 Outbox、Kafka 与 Worker

- LOCAL_TASK 和 KAFKA_TASK 共用业务 task、Processor、claim、lease、retry 与结果提交。
- Kafka 只新增发布适配和持久接入流程，不复制第二套 TaskService 与 WorkerExecutor。
- delivery callback、inbox admission、offset 提交各自有一次完成出口。
- Outbox 重试、消息接入重试、任务执行重试分别保留语义；可共享退避数学函数，不能合并为一个抹平提交边界的通用 RetryManager。
- 原模式实际使用中的适配保留；退出支持的迁移代码在验证完成后删除，不能长期保留无调用的旧分支。
- Protobuf 只维护 .proto 和业务校验；不手改或复制生成代码。

### 7.5 文件与处理器

ThumbnailProcessor、MetadataProcessor 只实现具体转换；输入校验、预算、attempt 命名、结果提交由公共执行路径负责。

图片和元数据产物的格式校验不同，不能为了复用把必要检查删掉。文件发布与 MySQL CAS 的边界保持显式，不做万能 StorageTransaction 假装跨资源原子提交。

Nginx 用配置完成入口职责；Python Runner 用有限步骤编排实验。二者都不扩展为新的通用平台。

## 8. 公共工具、错误与异步状态

### 8.1 公共工具提取规则

出现两处真实重复时先比较语义；出现第三处仍一致时优先提取。数字是检查提示，不是强制门槛；一次使用但能显著澄清复杂逻辑的局部函数同样合理。

要比较：单位、所有权、错误处理、调用线程和未来变化方向。仅仅代码文本相像，不足以合并。

公共模块只保留已使用能力。不为一个错误转换引入跨项目通用错误注册中心，不为几个字段引入模板反射/自动序列化框架。

### 8.2 错误传播

使用项目已有且验证过的 Status/StatusOr；新组件在边界转换第三方错误。保留 errno、数据库错误码或 Kafka 原因与请求上下文。

禁止同一调用链反复 Result → Status → Exception → Result。日志由能够采取动作的层记录，底层补上下文；同一个错误不在每层打印完整栈形成日志放大。

“少写 if”不是理由：参数范围、返回码、受影响行数、短写和事务未知状态的检查必须保留。

### 8.3 异步复杂度

一个实际操作使用一份状态对象管理期限与完成权，不按每个回调各造一个 Context/State/Session。完成回调最多调用一次，资源释放依据真实 I/O 完成，不能依据 HTTP 响应已返回提前释放。

引用仅用于生命周期明确的同步借用；异步保存引用必须证明所有者存活。不要把所有对象改成 shared_ptr 来省思考；也不要为减少 shared_ptr 行数牺牲正确生命周期。

已有回调模型可完成当前用例时，不再同时引入另一套自研协程运行时。若选择协程，必须复用成熟运行时并有明确迁移边界，不长期维护两套同义异步 API。

## 9. 测试与配置也要收敛

### 9.1 测试以行为为单位

每个关键协议选择一层主要证明：纯状态/算法用单元测试，真实库语义用集成测试，跨组件故障用场景测试。跨层测试可以重叠，但要覆盖新增边界。

相同输入结构、相同不变量的变体用参数化测试；不要复制几十份 setup/teardown。fixture helper 只抽取确定重复的准备步骤，不建设通用测试编排框架。

Mock 只模拟必要外部边界；不为每个内部类都生成 Fake 和 Mock。不要用精确调用次数代替用户可观察结果，除非次数本身就是限流或幂等约束。

测试代码可以超过生产代码比例，不设硬性比率。只有在行为覆盖等价时才合并测试；半关闭、过期 token、COMMIT_UNKNOWN、重复消息、旧 Worker 晚到不能为省行数删除。

### 9.2 配置按真实决策增加

只为部署差异或需要实验调节的参数增加配置。固定内部规则用清晰常量，不把每个私有变量都开放成配置项。

每个配置项只有一个默认值来源、一处 schema 校验和明确优先级；不同时维护冲突的 CLI/JSON/环境默认值。

不增加无用 feature flag，不同时实现 JSON/YAML/TOML 三套解析。既有有效配置兼容性需要保留时，给出迁移期限和测试后再移除旧入口。

## 10. 必须保留的正确性代码

| 领域 | 不能以收敛为由删除 |
|---|---|
| 网络 | EINTR/EAGAIN、短读短写、SO_ERROR、FIN 排空、RST 差异 |
| 生命周期 | owner、generation/token、取消、幂等 Close、once-completion |
| 调度 | ET 主动续跑、预算唤醒、无 token 不忙等 |
| 资源 | 队列/内存/连接/解码/在途操作上限 |
| 写入 | 幂等唯一约束、事务边界、COMMIT_UNKNOWN 与权威查询 |
| 缓存 | 超时、回源准入、版本/TTL 与陈旧边界 |
| 消息 | Outbox 重复、inbox admission、连续 offset、rebalance |
| Worker | generation/epoch 条件更新、lease、独立 attempt 文件 |
| 输入 | 请求与消息长度、字段范围、路径、图片尺寸与类型校验 |
| 验证 | 关键故障窗口证据、原始数据、失败测试与恢复记录 |

可以集中公共检查，不能默认外部输入已经校验；内部不变量可用类型和集中入口保障，避免在每个内部 helper 重复整套外部校验。

## 11. 已有代码的收敛流程

没有真实仓库时，下列只是审查顺序，不声称已经发现冗余。

1. **建立基线**：记录 commit、构建方式、当前测试和真实模块统计；保留用户未提交改动。
2. **画职责清单**：列入口、状态所有者和主要调用链，定位同义层与重复路径。
3. **先处理低风险冗余**：无调用且不承担兼容职责的内部实现、重复转换、重复 fixture、重复默认值。
4. **再合并同构逻辑**：双 Direction 推进、共用 task 执行协议、相同错误映射；逐项验证语义一致。
5. **移除无效中间层**：逐个迁移调用者，验证后删除旧层；不留 Old/New/Legacy 多套长期并存。
6. **最后调整状态与线程结构**：仅当所有权和不变量明确时进行，避免为了行数大改核心模型。
7. **形成可复查结果**：记录前后职责、新增/删除代码、相关测试；允许行数增加但逻辑更清楚。

不得把结构重构、行为修改、数据库 schema 升级和依赖大版本升级合并成一次无法定位问题的改动。每批只围绕一条连续职责，保持可以构建和回退。

删除前检查静态调用、注册入口、配置引用与外部 API；“rg 没找到名字”不是唯一死代码证据。公共 API 或 migration 的兼容要求先核实。

## 12. 何时触发设计复查

| 信号 | 默认动作 |
|---|---|
| 模块超过目标 25% | 查重复路径、包装层和后续剩余工作 |
| 连续两组主要新增 Factory/Manager/Context，却没有新行为 | 合并职责或延后未使用抽象 |
| 一个功能必须同步改三套同形模型/状态表 | 明确权威来源，减少人工映射 |
| Kafka 阶段重新实现 TaskExecutor/Processor | 改为复用原执行与提交路径 |
| 多个类只调用下一层且不承担约束 | 删除空转层或合并 |
| 新增大量模板参数仅用于一个场景 | 改成具体实现或少量普通参数 |
| 改一个策略需要修改所有策略 | 检查真正变化点，增加必要边界，允许合理增码 |
| 代码已经短，但条件组合和 bool 参数难解释 | 显式状态/类型拆分，允许增码 |
| 新测试主要重复已有 setup 与相同断言 | 参数化或复用 fixture，保留新增边界 |
| 为了省代码而无法解释关闭/提交时机 | 恢复显式协议后再收敛 |

提示阈值不是机械 lint 门禁。复查结论可以是“保留，必要复杂度”；记录真实原因后继续必要工作。

## 14. 教学与代码生成约束

1. 先给本组相关目录与函数签名，再给新增代码/diff。
2. 只创建本组需要的文件；未来目录与接口可以写在计划中，不生成空壳源码。
3. 复用已有 CMake、日志、Status、Buffer 和测试基线，禁止换窗口后重新造一套。
4. 不一次输出整个完整仓库；以能解释和验证的一条路径推进。
5. 不把教学伪代码、临时演示和生产实现并行保留在生产目录。
6. 不为“方便教学”复制完整函数到多个文件；源码是唯一权威实现。
7. 发现蓝图可以用更少的合理层次实现时，解释映射并按规则实施，不机械复刻类名。
8. 扩展 Kafka、Nginx、监控等按既定阶段推进，不在当前阶段预生成完整插件体系。
9. 当用户能解释已有机制时减少重复授课，把时间用于新增行为和关键错误路径。
10. 换窗口更新 state.md；本约束文档只在规则变化时更新，不追加聊天流水账。

本次规则文件与原蓝图配合使用；无需再创建单独的抽象登记表、代码行数日报或新状态文档。例外理由放已有 DECISIONS.md，真实缺陷放 BUG_LEDGER.md。
